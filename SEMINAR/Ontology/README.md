## 발표자 및 배경
발표자는 김태영(AIFactory 대표이사, Microsoft RD & AI MVP, LangChain Ambassador)로, 한국항공우주연구원 연구원 출신이며 Nature Astronomy 공동 1저자 이력이 있다. 2020년 창업한 AIFactory는 이후 AssiWorks(tool/flow/operator, air/loop 등)라는 에이전트 오케스트레이션 플랫폼을 출시해왔다. 이번 발표는 "온톨로지를 하네스(harness)에 결합하면 LLM 에이전트가 왜, 어떻게 더 정확해지는가"를 이론과 실측 실험 양쪽으로 다룬다.

## 1. 문제의식 — 왜 프롬프트만으로는 부족한가

발표는 먼저 AI 엔지니어링의 발전 단계를 하나의 계보로 정리한다.

| 단계 | 목적 | 방식 |
|------|------|------|
| ML/DL 피처·모델 엔지니어링 | 높은 정확도 | 특정 태스크 수행 |
| LLM 프롬프트 엔지니어링 | 똑똑하게 만들기 | 맥락 주입 by 사람, 도구 호출 by 사람 |
| Context Agent 컨텍스트 엔지니어링 | 맥락 이해 높이기 | 맥락 주입 by 시스템, 도구 호출 by 사람 |
| Tool Calling Agent 에이전틱 엔지니어링 | 일 잘하게 만들기 | 맥락·도구 호출 by AI, 도구 생성 by 사람 |
| Coding Agent **하네스 엔지니어링** | 믿고 맡기기 | 맥락 주입·도구 호출·도구 생성 모두 by AI |

이 흐름에서 "하네스 엔지니어링"이란 에이전트가 프로젝트의 지침(Instruction)·도구(Tool)·환경(Environment)·상태(State)·피드백(Feedback) 5요소를 스스로 다루며 자율적으로 지식을 쌓고 실행하는 단계를 뜻한다. 실제 사례로 `github.com/revfactory/harness`(Claude Code 기반 하네스 자동 구성 도구, Phase 0 현황감사 → Phase 7 하네스 진화까지 8단계 워크플로우)와 `walkinglabs.github.io/learn-harness-engineering` 가이드라인을 인용한다.

### 좋은 하네스의 5요소와 에이전트 실패 체크리스트
| 요소 | 역할 | 대표 산출물 |
|------|------|-------------|
| 지침 Instruction | 프로젝트 개요·규칙·실행법·금지사항 | AGENTS.md, CLAUDE.md |
| 도구 Tool | 에이전트가 실제 행동하게 함 | shell, git, test runner, MCP |
| 환경 Environment | 재현 가능한 실행 환경 | Docker, devcontainer, pyproject.toml |
| 상태 State | 세션 간 기억 유지 | PROGRESS.md, DECISIONS.md |
| 피드백 Feedback | 완료 여부의 객관적 판정 | pytest, mypy, ruff, E2E test |

에이전트가 실패했을 때 점검할 5가지 질문(Task specification, Context provision, Execution environment, Verification feedback, State management)을 제시하고, "바이브 코딩"(직관적으로 코드만 작성)과 "하네스 엔지니어링"(환경 설계·의도 표현·피드백 루프까지 구축)을 대비시킨다.

### 지식관리의 문제
시니어의 잡담, 동료의 슬랙, 고객의 이메일, 문서 파일 등 조직의 지식이 사람에게만 흘러가고 에이전트에게는 닿지 않는 구조를 지적하며, 이를 AGENT.md/README·ARCHITECTURE.md·Makefile/init.sh·테스트/정적분석 명령·PROGRESS.md 같은 파일로 "컨텍스트 정리"해두면 새 세션도 사람에게 묻지 않고 시작할 수 있다고 설명한다. 이 과정에서 지식 가시성 격차, 시스템 오브 레코드, 콜드 스타트 테스트, 발견 비용, 지식 부패율 같은 개념과, 단일 파일 대신 분산·라우팅 파일·점진적 공개 구조로 컨텍스트 비대화·중간 손실 효과·우선순위 모호성을 줄이는 방법을 제시한다.

## 2. 예제 도메인 — 휴가 전자결재

이후 모든 논증은 하나의 예제로 검증된다: 직원 4명(김민준-사원, 이수진-책임, 박서준-팀장, 정유진-본부장)의 결재 라인(`reports_to`)과 잔여 연차, 그리고 3개 규칙으로 구성된다.

- **R1** 승인자 = 직속상관 (`approver == requester.reports_to`)
- **R2** 신청 일수 ≤ 잔여 연차 (`days <= requester.leave_balance`)
- **R3** 자기 결재 금지 (`approver != requester`)

## 3. 문제 시연 — 프롬프트만으로는 규칙을 지킬 수 없다

"신입 김민준 휴가 12일 결재 상신해줘. 승인은 이수진 책임한테."라는 프롬프트를 그대로 실행하면 `{승인자: 이수진, 12일}`이 만들어지는데, 실제로는 이수진은 김민준의 직속상관이 아니며(R1 위반, 실제 상관은 박서준), 신청 일수도 잔여 연차 8일을 초과한다(R2 위반). 이는 회사의 "사실"(결재 라인)과 "규칙"(정책)이 프롬프트 밖에 있기 때문이며, 발표는 이를 세 가지 한계로 정리한다: **사실·관계 환각**(모르는 관계를 지어내거나 잘못 수용), **해석 비일관성**(팀장/직속상관/윗사람을 매번 다르게 해석), **규칙 검증 불가**(만족 여부를 확인·차단할 장치 없음). 검토 없이 이런 산출물이 통과되면 반려·재작업·감사 리스크가 발생하고, 사람이 매번 사후 검토해야 하므로 자동화 효과가 사라진다.

## 4. 온톨로지란 무엇인가

온톨로지는 도메인의 엔터티·관계·규칙을 코드나 프롬프트가 아니라 "데이터"로 적은 형식 지식이다. 발표는 RDF 트리플(주어-술어-목적어)을 최소 단위로 소개한 뒤, 그 위에 OWL로 논리적 공리(axiom)를 얹는 과정을 실제 스키마(`leave.ttl`)로 보여준다.

```
:Employee a owl:Class .  :Manager a owl:Class .
:reportsTo a owl:ObjectProperty ; rdfs:domain :Employee ; rdfs:range :Employee .
:hasSuperior a owl:ObjectProperty, owl:TransitiveProperty .
:reportsTo rdfs:subPropertyOf :hasSuperior .
:manages a owl:ObjectProperty ; owl:inverseOf :reportsTo .
:Manager owl:equivalentClass [ a owl:Restriction ; owl:onProperty :manages ; owl:someValuesFrom :Employee ] .
```

### OWL-RL 추론 — 왜 이 프로파일을 쓰는가
OWL에는 표현력과 계산복잡도가 다른 여러 프로파일이 있는데, 이 발표는 **OWL 2 RL**을 사용한다. OWL 2 RL은 IF-THEN 규칙 기반의 전방 연쇄(forward-chaining) 추론으로 데이터 크기에 대해 다항 시간에 동작하며, 추론 결과를 실제 트리플로 그래프에 추가(구체화)해두므로 이후 질의는 단순 조회가 된다. 다만 복잡한 클래스 교집합이나 전칭 제약(`allValuesFrom`)의 일부, 비결정적 추론 등 완전한 OWL DL 추론은 지원 범위 밖이라는 한계도 함께 설명한다 — 이는 W3C OWL 2 프로파일 명세와 부합하는 정확한 설명이다.

실제로 사용된 엔테일먼트 규칙: **prp-spo1**(하위 속성 전파: `reportsTo` → `hasSuperior`), **prp-trp**(추이 속성: 상급의 상급도 상급, 스킵레벨 관계 도출), **prp-inv1/2**(역관계: `reportsTo`의 역으로 `manages` 도출), **cls-svf1 + scm-eqc**(`someValuesFrom` 분류: 누군가를 `manages`하면 `Manager` 클래스로 자동 분류). Python의 `rdflib` + `owlrl` 라이브러리(`owlrl.DeductiveClosure(owlrl.OWLRL_Semantics).expand(g)`)로 구현하며, 더 이상 새 트리플이 생성되지 않는 고정점(fixed point)까지 규칙을 반복 적용한다.

예제 조직 데이터에 대해 3라운드 만에 고정점에 도달하는데, 그 결과 "김민준의 상급자는 박서준·정유진이다"(스킵레벨, 원본에 저장되지 않은 사실)와 "박서준·정유진은 Manager이다"(분류, 마찬가지로 저장되지 않은 사실)가 새로 도출된다. 여기에 "직속상관이 휴가 중이면 그 위 가용 상급자에게 위임"이라는 R1의 위임 조건을 결합하면, "박서준이 휴가 중"이라는 사실 + 추론된 상급자 체인 + 위임 규칙이 합쳐져 "이 건의 가용 승인자 = 정유진"이라는, 어디에도 명시적으로 저장되지 않은 결론이 도출된다.

## 5. 아키텍처 — 온톨로지 레이어 × 에이전틱 루프

에이전틱 루프(프롬프트 해석 → 컨텍스트 수집 → 수행 → 결과 검증 → 산출물)의 각 단계에 온톨로지 레이어가 서로 다른 지식을 공급하고, 검증 실패 시 "중단·조정" 경로로 되먹임해 스스로 교정한다.

| 게이트 | 역할 | 온톨로지가 주는 것 | 없으면 |
|--------|------|---------------------|--------|
| ① 해석 (`interpret`) | 자연어 → 표준 개념 | lexicon(동의어 사전) + 등재 엔터티만 인정 | 역할어 오해석 (예: '팀장' 미해결) |
| ② 수집 (`gather_context`) | 관련 사실(subgraph) 모음 | 추이폐포·역관계 등 추론된 서브그래프 | 숨은 사실 누락 |
| ③ 제약 (`constraints`) | 추상 규칙 → 이 건의 구체 조건 | 위임까지 반영된 구체 제약값 | 자유 생성으로 인한 오류 |
| ④ 검증 (`validate`) | 규칙 위반 여부 점검 | 결정적(deterministic) 판정 기준 | 검증 자체가 불가능 |
| ⑤ 조정 (`adjustment_info`) | 교정 정보 생성 또는 인계 | 위반 규칙 ID 기반 조정 근거 | 오류가 방치된 채 통과 |

전체 하네스 루프는 `intent=interpret(prompt)` → `ctx=gather_context(intent)` → `constraints=constraints(intent)` → 반복문(`action=agent.propose(...)` → `violations=validate(action)` → 위반 없으면 출고, 있으면 `adjustment=adjustment_info(...)`로 재수행) → 수렴 실패 시 `escalate_to_human()`이라는 약 10줄의 의사코드로 요약된다. **온톨로지 유무(OFF/ON)의 차이는 오직 이 2~5단계에 온톨로지를 연결했는지 여부뿐**이라는 점이 이후 비교 실험의 핵심 통제 변수다.

## 6. 실제 구동 트레이스 (결정론적 시뮬레이션)

"신입 김민준 휴가 12일 결재 상신해줘. 승인은 이수진 책임한테."를 하네스에 넣으면: ① 해석 결과 `{신청자: 김민준, 승인자후보: 이수진, 일수: 12}` → ② 수집으로 직속상관=박서준, 잔여=8, 규칙 R1·R2·R3 확보 → ③ 제약으로 `{approver_must_be: 박서준, days_max: 8, approver_not: 김민준}` 확정 → ④ 1라운드 수행 결과 `{박서준, 12}`가 검증에서 R2 위반 적발 → ⑤ 조정으로 `days=8` 제시 → 2라운드 수행 결과 `{박서준, 8}`이 검증 통과 → **정상 출고 (자기교정 2라운드, 사람 개입 없음)**.

## 7. OFF vs ON 비교 및 4개 시나리오

같은 mock 에이전트·같은 입력에서 `use_ontology` 플래그만 바꾼 통제 비교 실험이다.

- **OFF**: 컨텍스트·제약·검증 게이트가 전혀 없어 프롬프트를 문자 그대로 수행 → `{이수진, 12일}`이 규칙 위반(R1·R2) 상태로 그대로 출고됨.
- **ON**: 제약이 R1을 사전에 예방하고, 검증·조정 루프가 R2를 잡아내 `{박서준, 8일}`로 정상 출고 (2라운드).

| 시나리오 | 강조 게이트 | OFF 결과 | ON 결과 |
|----------|-------------|----------|---------|
| S1 — 역할어 해소 ("팀장한테") | ① 해석 | `{김민준,3일}` ✗ (R1·R3, '팀장' 미해결로 본인 처리) | `{박서준,3일}` ✓ |
| S2 — 숨은 사실 (잔여 연차 모름) | ②+④ | `{박서준,12일}` ✗ (R2) | `{박서준,8일}` ✓ (2라운드) |
| S3 — 복합 오류 (승인자+한도 동시 위반) | ③+⑤ | `{이수진,12일}` ✗ (R1·R2) | `{박서준,8일}` ✓ (2라운드) |
| S4 — 위임 불가 (본부장 본인 신청) | ⑤ 안전중단 | `{정유진,5일}` ✗ (R3, 본인 승인) | 가용 상급자 없음 → **사람에게 인계** |

S4는 자동화가 무조건 정답을 내는 게 아니라, "틀린 답 대신 멈추는 것"도 온톨로지 기반 하네스의 유의미한 효능임을 보여주는 사례로 제시된다.

## 8. 실측 실험 — 실제 `claude -p` 에이전트로 검증

목업이 아니라 실제 `claude -p` 에이전트(동일 모델, 조건만 변경)를 피험자로 세우고, **정답은 별도의 OWL 추론기(rdflib+owlrl)가 결정적으로 산출**한 값을 기준으로 게이트별 정답률을 측정했다. 조직 규모(5명 → 51명 → 1,971명)와 컨텍스트 형식(정보없음 / 평문(raw) / 온톨로지 구조 / 온톨로지+추론)을 교차시켜 최대 1,500여 건(다른 슬라이드 기준 990건)을 병렬·시드 고정으로 재현 가능하게 실행했다.

### 4개 대표 케이스 (실제 `claude -p` 최종 결재 결과)
| 케이스 | 강조 게이트 | 온톨로지 전무 | 온톨로지+추론 | 정답 |
|--------|-------------|----------------|------------------|------|
| A (해석·위임) | ① | `{팀장,3}` ✗ | `{정유진,3}` ✓ | `{정유진,3}` |
| B (검증·잔여) | ④ | 인계 ✗ | `{정유진,12}` ✓ | `{정유진,12}` |
| C (복합) | ③+⑤ | `{이수진,12}` ✗ | `{정유진,8}` ✓ | `{정유진,8}` |
| D (안전중단) | ⑤ | 인계 ✓ | 인계 ✓ | 인계 |

온톨로지 전무 1/4 → 온톨로지+추론 4/4.

### 중간 규모(51명)에서 컨텍스트 형식별 게이트 정답률(%)
| 게이트 | 정보없음 | 평문 | 온톨로지(구조) | 온톨로지+추론 |
|--------|----------|------|------------------|------------------|
| 전체 | 25 | 95 | 95 | 95 |

이 규모에서는 필요한 정보가 컨텍스트에 다 들어가기만 하면 평문이든 온톨로지든 형식은 정확도에 거의 영향을 주지 않는다 — 발표 스스로도 이를 "정보가 다 들어가면 형식 무차별"이라고 명확히 인정한다.

### 규모에 따른 역전 — 초대규모(1,971명)
| 게이트 | 전무 | 사실 일부("다 넣기") | 온톨로지+추론 |
|--------|------|------------------------|------------------|
| 전체 | 36 | 37 | 95 |

소규모(5명)에서는 "그냥 다 넣기"와 온톨로지가 동률(97=97)이지만, 조직 규모가 커져 모든 사실을 컨텍스트에 다 넣을 수 없게 되면 "다 넣기" 방식은 아무것도 안 넣은 것과 비슷한 수준(37%)으로 붕괴하는 반면, 온톨로지+추론은 95%를 유지한다. 특히 ②수집·③제약·⑤조정 게이트가 규모가 커질수록 가장 먼저 무너지는 지점으로 지목된다.

### 효용의 실제 원천 — "추론"이 아니라 "검색"
초대규모에서 온톨로지를 추론 없이(관련 서브그래프만 주입) 사용한 경우와 추론을 포함한 경우의 정답률이 사실상 동일(둘 다 95%)하다는 결과는, **온톨로지의 1차 가치가 논리 추론 자체가 아니라 "관련된 사실만 정확히 검색해 주입하는 것"**에 있음을 시사한다 — 관련 서브그래프만 넣어주면 LLM이 스스로 남은 추론(상급자 체인 등)을 수행할 수 있었다는 뜻이다. 이는 이 발표에서 가장 주목할 만한 반직관적 결론으로, 온톨로지 도입의 정당화 논리를 "정교한 추론기"가 아니라 "정확한 검색/컨텍스트 구성"에 두어야 한다는 시사점을 준다.

### 일관성(결정성) 실험
같은 어려운 위임 입력을 5회 반복 실행했을 때, "사실 일부만 주입" 조건은 해석·수집·제약·조정 게이트에서 답이 흔들려 5회 중 정답이 0회인 경우가 많았던 반면, **온톨로지+추론 조건은 모든 게이트에서 5/5 결정적으로 동일한 정답을 냈다**. 발표는 이를 두고 "정확도가 아니라 결정성·감사가능성이 핵심 가치"라고 정리한다.

## 9. 결론 — 왜 온톨로지 기반이 더 나은가

규칙을 프롬프트 문장 속에 묻어두는 대신 데이터(온톨로지)로 분리했을 때 얻는 6가지 이점으로 마무리된다: **정확성**(관계를 환각 없이 사실로 해석), **일관성**(공유 의미론으로 같은 표현이 같은 뜻을 가짐), **검증가능성**(규칙이 형식적 게이트가 되어 미통과 시 미출고), **자기교정**(위반 시 조정 정보로 루프가 수렴), **유지보수성**(정책이 바뀌면 온톨로지 파일만 수정), **설명가능성**(모든 교정 내역이 규칙 ID로 추적 가능).

## 10. 부록 — 실제 적용 사례

발표 말미에는 AIFactory의 실제 제품/프로젝트에 이 개념이 적용된 사례들이 스크린샷과 함께 소개된다.
- **AssiWorks Loop**: 클라우드 코딩 세션 플랫폼으로, 세션 생성 시 "Loop Agent"(사내 자율 모드) 또는 "Claude Code"(OAuth 로그인) 중 선택하고, API Builder(FastAPI)·ML Trainer·Mobile(React Native)·Paper Mate 등 미리 정의된 "하네스" 프리셋 중 하나를 골라 시작하는 UI를 시연한다 (예: "MNIST 분류 정확도가 높은 모델을 만들어" 요청 시 ML Trainer 하네스가 CNN 모델 코드를 작성).
- **Onto-OSINT**: 온톨로지 기반 OSINT(공개출처정보) 일일 보고서 자동 생성 시스템. 수집(Collector)·추출(Extractor)·추론(Reasoner)·보고(Reporter) 4개 에이전트가 각자의 참고 규칙 파일을 근거로 협업하며, 새 정보가 기존 온톨로지로 분류 불가능할 경우 가설을 세우고 같은 패턴이 3건 이상 반복되면 스키마를 확장(근거는 changelog에 기록)하는 온톨로지 진화 절차를 갖는다. "북한 핵활동"과 "지구관측 이벤트(위성영상 기반 재해·환경 모니터링)" 두 도메인의 실제 일일 보고서 예시가 포함되어 있으며, 다중 위성 교차검증·공식 출처 신뢰도 가산·한반도 가중치 등 신뢰도 산정 규칙과 그 산출 근거가 상세히 제시된다.
- **Onto-Sat-Scene**: 위성영상 장면(Scene)에 대한 온톨로지 기반 검색 시스템으로, 온톨로지 빌더(OWLReady2 + HermiT/Pellet 추론기) → 트리플 스토어(Ontotext GraphDB) → 검색/RAG 레이어(OpenSearch BM25 + Qdrant 벡터 임베딩) → 에이전트 브릿지(FastAPI, 의도 라우터, SPARQL 화이트리스트 가드, 사람 검토를 거치는 `/evolve` 스키마 진화 엔드포인트)의 4계층 구조를 가진다. "산사태"라는 단어가 없어도 "최근 폭우 이후 변화가 큰 장면"처럼 의미 기반으로 관련 장면을 찾아내는 시연과, 신규 개념("Pass" 클래스)을 사람 검토 후 온톨로지에 실시간으로 추가·재색인하는 시연이 포함된다.
